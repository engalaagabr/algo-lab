# رحلة AlgoLab من الفرونت إلى الخوارزمية — شرح بالعربي

الوثيقة دي بتشرح إزاي الطلب يبدأ من اختيار المستخدم في الواجهة، يوصل للـAPI، يتنفذ داخل
الخوارزمية، ويرجع كبيانات تحدّث الواجهة. بعدها هتلاقي شرحًا لكل خوارزمية: بتاخد إيه، بتعمل
إيه، وبتطلع إيه.

> **حالة الفرونت:** الفرونت المشترك موجود في مجلد `frontend/` (Vite + React + TypeScript)،
> وطريقة تشغيله في [frontend/README.md](../frontend/README.md). تدفق العمل الموضح هنا هو العقد
> الذي ينفذه الفرونت مع الـAPI الحالي.

## 1. الصورة الكبيرة

الـbar مش بيتبعت لوحده للخوارزمية. كل bar بيمثل رقمًا داخل مصفوفة، والواجهة تبعت **المصفوفة
كاملة** ومعاها أسماء الخوارزميات المختارة. كل خوارزمية تشتغل على نسخة من نفس الأرقام.

```mermaid
flowchart LR
    U[اختيارات المستخدم] --> F[الفرونت: حالة وتجهيز الطلب]
    F -->|JSON عبر HTTP| V[FastAPI: استقبال والتحقق]
    V --> R[Runner: إرسال مهمة لعامل CPU]
    R --> S[Application service]
    S --> A[الخوارزميات المختارة]
    A -->|ناتج وقياسات وأحداث| S
    S --> R --> V -->|JSON response| F
    F -->|تحديث الحالة وعرض bars| U
```

الفرونت مسؤول عن المدخلات، عرض الأخطاء، تخزين حالة الشاشة، وتشغيل الأنيميشن. الباك إند مسؤول
عن صحة المدخلات، تنفيذ الترتيب، حساب القياسات، وتكوين قائمة أحداث العرض. التحكم في Play وPause
وStep وReset يحصل في الفرونت بعد استلام الأحداث؛ مافيش endpoint لكل خطوة.

## 2. شكل المصفوفة والـbar

لو كانت المصفوفة:

```text
[5, -2, 3, 3, 0]
```

يبقى عندنا خمسة bars. كل bar مرتبط بفهرس ثابت في **النسخة المعروضة**:

| الفهرس | القيمة | اللي يمثله الـbar |
|---:|---:|---|
| 0 | 5 | العنصر الأول |
| 1 | -2 | العنصر الثاني، تحت خط الصفر |
| 2 | 3 | العنصر الثالث |
| 3 | 3 | العنصر الرابع؛ التكرار مسموح |
| 4 | 0 | bar عند خط الصفر |

ارتفاع العمود بيمثل مقدار القيمة. للقيم السالبة، الارتفاع يظهر أسفل خط الصفر. الخوارزمية نفسها
لا تعرف أي شيء عن الـbars أو HTML؛ هي تتعامل مع قائمة أعداد فقط.

## 3. دورة الاستخدام في الفرونت

### أ. تحميل الصفحة

الفرونت يبدأ بطلبين:

```http
GET /health
GET /api/v1/algorithms
```

الأول يتأكد إن API شغال. الثاني يرجع قائمة الخوارزميات ومع كل واحدة الاسم والـID والوصف
والتعقيد والحد الأقصى. الفرونت يبني قائمة الاختيارات من الرد بدل ما يكرر بيانات الخوارزميات
داخل كوده.

أمثلة IDs:

```text
selection_sort  bubble_sort  odd_even_sort  cocktail_sort
insertion_sort  binary_insertion_sort  frequency_sort
shell_sort      heap_sort    quick_sort
```

### ب. المستخدم ينشئ بيانات

لو المستخدم اختار حجمًا ومدى ونمطًا، يرسل الفرونت:

```http
POST /api/v1/datasets
Content-Type: application/json
```

```json
{
  "size": 5,
  "minimum": -5,
  "maximum": 10,
  "distribution": "random",
  "seed": 42
}
```

السيرفر يرجع القيم التي وُلّدت فعلًا، مثل:

```json
{
  "values": [5, -2, 3, 3, 0],
  "seed": 42,
  "size": 5,
  "minimum": -5,
  "maximum": 10,
  "distribution": "random"
}
```

الفرونت يخزن `values` في حالة الصفحة ويرسم منها الأعمدة. الـseed هنا خاص بتوليد المصفوفة؛ لو
أعدت نفس إعدادات التوليد والـseed، تقدر تعيد إنشاء نفس البيانات في هذا الإصدار.

الأنماط المتاحة: `random` عشوائي، `sorted` مرتب، `reversed` عكسي، `nearly_sorted` شبه مرتب،
و`few_unique` يحتوي حتى خمس قيم مميزة.

### ج. المستخدم يختار خوارزميات

الفرونت يحفظ IDs المختارة في حالة محلية، مثل:

```js
selectedAlgorithmIds = ["bubble_sort", "quick_sort"];
```

اختيار الخوارزمية لا يبدأ التنفيذ وحده. عند الضغط على **Visualize**، الفرونت يرسل المصفوفة
الحالية والـIDs المختارة إلى `/sort`.

### د. طلب العرض المرئي

```http
POST /api/v1/sort
Content-Type: application/json
```

```json
{
  "values": [5, -2, 3, 3, 0],
  "algorithm_ids": ["bubble_sort", "quick_sort"],
  "trace": true
}
```

الـAPI يتحقق من JSON والحدود. بعدها خدمة التجارب تعمل الآتي لكل خوارزمية:

1. تنسخ الإدخال الأصلي، بحيث لا تغيّر خوارزمية بيانات خوارزمية أخرى.
2. تشغّل الخوارزمية لعدّ المقارنات والتبديلات والكتابات.
3. لو `trace: true`، تشغّل نسخة أخرى وتجمع أحداث المقارنة والتغيير بترتيبها.
4. تتحقق أن الناتج يساوي ترتيب Python المرجعي `sorted(values)`، بما يشمل الأرقام المكررة.
5. ترجع النتيجة بعد اكتمال التنفيذ.

الرد المبسط شكله:

```json
{
  "input_values": [5, -2, 3, 3, 0],
  "results": [
    {
      "algorithm_id": "bubble_sort",
      "output_values": [-2, 0, 3, 3, 5],
      "metrics": {
        "comparisons": 10,
        "swaps": 6,
        "array_writes": 12,
        "auxiliary_writes": 0,
        "writes": 12
      },
      "events": [
        {"sequence": 0, "kind": "compare", "indices": [0, 1], "values": [5, -2]},
        {"sequence": 1, "kind": "swap", "indices": [0, 1], "values": [-2, 5]}
      ]
    }
  ]
}
```

الأرقام في المثال التوضيحي؛ الرد الفعلي يحتوي جميع الأحداث إلى نهاية الترتيب. كل عنصر في
`results` يخص خوارزمية واحدة، وبنفس ترتيب `algorithm_ids` المرسل.

في فرونت JavaScript، جزء تجهيز حالة العرض ممكن يكون بالشكل ده:

```js
async function requestVisualization(apiBase, values, algorithmIds) {
  const response = await fetch(`${apiBase}/api/v1/sort`, {
    method: "POST",
    headers: { "Content-Type": "application/json" },
    body: JSON.stringify({ values, algorithm_ids: algorithmIds, trace: true }),
  });

  const body = await response.json();
  if (!response.ok) {
    throw new Error(body.error?.message ?? `Request failed: ${response.status}`);
  }

  return body.results.map(result => ({
    algorithmId: result.algorithm_id,
    values: [...body.input_values],
    outputValues: result.output_values,
    metrics: result.metrics,
    events: result.events,
    cursor: 0,
  }));
}
```

الفرونت يحفظ النتيجة التي ترجع من الدالة في state بتاعة الشاشة، ويطلب إعادة الرسم. `values`
هنا نسخة بداية مستقلة لكل خوارزمية، و`events` هو سجل العرض، و`cursor` يحدد الحدث التالي.
الواجهة تختار framework لاحقًا؛ منطق الطلب والعقد يفضل كما هو.

### هـ. الفرونت يحدّث العرض ويشغّل الأحداث

بعد وصول الرد، الفرونت يحتفظ بنسخة من `input_values` لكل خوارزمية، ويحتفظ بقائمة `events`
ومؤشر تشغيل `cursor` لكل واحدة. على سبيل المثال:

```text
Bubble player: values=[5,-2,3,3,0], cursor=0
Quick player:  values=[5,-2,3,3,0], cursor=0
```

كل ما يتقدم التشغيل، يقرأ الفرونت الحدث الحالي:

| `kind` | ماذا يفعل الفرونت؟ |
|---|---|
| `compare` | يلوّن العناصر المشار إليها في `indices`. لا يغيّر القيم. استخدم `values` لعرض طرفي المقارنة. |
| `swap` | يحدّث الخانتين المشار إليهما. `values` هنا هي القيم **بعد التبديل**؛ إسنادها مباشرةً للخانتين مناسب. |
| `write` | يضع القيمة الجديدة في الفهرس المشار إليه. |

في `compare` قد يرجع `indices` بفهرس واحد فقط مع قيمتين. مثال Insertion Sort يحتفظ بقيمة
`key` خارج المصفوفة ويقارنها بعنصر موجود داخلها؛ لذلك لا تخمّن فهرسًا للقيمة المحفوظة.

زر **Step** يحرك كل خوارزمية غير مكتملة حدثًا واحدًا. لو خوارزمية انتهت قبل البقية، تظل
مصفوفتها كما هي بينما تكمل البقية. زر **Play** يطبق الأحداث تلقائيًا حسب سرعة العرض. زر
**Pause** يوقف المؤقت المحلي. زر **Reset** يرجّع النسخ والمؤشرات إلى البداية من غير طلب جديد
من السيرفر. بعد اكتمال الأحداث، المفروض أن تكون كل المصفوفات مساوية لـ`output_values`.

عداد التقدم `cursor / events.length` هو تقدم العرض، مش نسبة وقت التنفيذ. و`metrics` أرقام
العملية الكاملة من البداية للنهاية؛ لا تقلّ أثناء ضغط Step.

### و. قياس الأداء لا يستخدم أحداث العرض

عند الضغط على **Run benchmark**، الفرونت يرسل نسخة القيم الأصلية إلى:

```http
POST /api/v1/benchmarks
Content-Type: application/json
```

```json
{
  "values": [5, -2, 3, 3, 0],
  "algorithm_ids": ["bubble_sort", "quick_sort"],
  "repeats": 5,
  "warmups": 1,
  "seed": 42
}
```

`repeats` عدد القياسات، و`warmups` عدد مرات الإحماء قبل القياس. `seed` هنا يخلط ترتيب
الخوارزميات بين الجولات لتقليل أفضلية من تبدأ دائمًا؛ لا ينشئ المصفوفة ولا يثبت الوقت.

الرد يحتوي مثلًا على:

```json
{
  "input_values": [5, -2, 3, 3, 0],
  "seed": 42,
  "repeats": 5,
  "warmups": 1,
  "results": [
    {
      "algorithm_id": "quick_sort",
      "output_values": [-2, 0, 3, 3, 5],
      "metrics": {
        "comparisons": 12,
        "swaps": 2,
        "array_writes": 4,
        "auxiliary_writes": 2,
        "writes": 6
      },
      "samples_ns": [4100, 3900, 4300, 4000, 4200],
      "median_ns": 4100,
      "min_ns": 3900,
      "max_ns": 4300,
      "spread_ns": 400
    }
  ],
  "fastest_algorithm_ids": ["quick_sort"],
  "noise_warning": false
}
```

`median_ns` هو الوسيط الذي يرتب عليه البرنامج نتيجة التجربة. `min_ns` و`max_ns` يوضحان مدى
تغير العينات، و`spread_ns = max_ns - min_ns`. `noise_warning` تحذير من تداخل نطاقات القياس،
وليس اختبارًا إحصائيًا. قياس الزمن منفصل عن عدّ العمليات وعن تشغيل أحداث العرض؛ لذلك سرعة
الأنيميشن لا تدخل في الزمن.

### ز. مقارنة أحجام وأنماط

لجدول تجارب، يستخدم الفرونت:

```http
POST /api/v1/benchmark-suites
Content-Type: application/json
```

```json
{
  "algorithm_ids": ["insertion_sort", "heap_sort", "quick_sort"],
  "sizes": [16, 64],
  "distributions": ["random", "reversed"],
  "minimum": -100,
  "maximum": 100,
  "seed": 42,
  "repeats": 5,

```

ده ينشئ أربع حالات: كل حجم مع كل نمط. كل الخوارزميات في الحالة نفسها تستقبل نفس القيم. الرد
في `cases`، وكل حالة فيها بياناتها `dataset` ونتائج القياس `benchmark`. الحد الأقصى 12 حالة
في الطلب.

### ح. الأخطاء في الواجهة

الرد الناجح يكون HTTP `200`. عند الخطأ يظهر رد على النمط:

```json
{
  "error": {
    "code": "limit_exceeded",
    "message": "..."
  }
}
```

الفرونت يقرأ HTTP status و`error.code`، ويعرض `message` للمستخدم. أشهر الحالات: `404`
خوارزمية غير معروفة، `422` مدخلات أو حدود غير مقبولة، `413` جسم طلب أكبر من حد 1 MB، و`503`
العامل مشغول أو غير متاح. الـhealth ممكن يظل `ok` حتى لو طابور تنفيذ التجارب مشغولًا؛ كل
endpoint هو الذي يوضح حالته.

الفرونت المشترك موجود داخل `frontend/` في جذر الريبو. أثناء التطوير يشتغل على
`localhost:5173`، وخادم Vite يمرر طلبات `/api` و`/health` للباك إند، فالمتصفح يكلم نفس الـorigin
ومش محتاجين CORS. لو الفرونت اتنشر على origin مختلف عن الـAPI، لازم `ALGOLAB_CORS_ORIGINS` يحتوي
**نفس origin** الذي فتح منه المتصفح. إعداد Docker الحالي يشغل الباك إند فقط؛ يضاف frontend
service إلى Compose لاحقًا.

## 5. كيف تعمل الخوارزميات؟

### العقد المشترك لكل الخوارزميات

داخل Python، الدالة تستقبل كائن `SortContext`، مش request من الويب ولا عنصر bar. المصفوفة
الموجودة في `context.values` هي نسخة عمل خاصة بهذه الخوارزمية. الدالة ترتبها **in-place**
وترجع ضمنيًا `None`؛ التطبيق يأخذ المصفوفة بعد تعديلها ويضع نسخة منها في `output_values`.

الخوارزمية تستخدم:

- `context.compare(a, b, indices)`: تقارن قيمتين، وتزيد عداد المقارنات إذا كان العد مفعّلًا.
- `context.swap(i, j)`: تبدّل عنصرين، وتزيد عدد التبديلات وكتابات المصفوفة.
- `context.write(i, value)`: تكتب قيمة في المصفوفة وتسجل حدث كتابة عند طلب trace.
- `context.auxiliary_write()`: يسجل الكتابة في بنية مساعدة، مثل جدول التكرارات.

العداد `comparisons` يحصي مقارنة قيمتين عن طريق `compare`؛ لا يحصي كل مقارنة فهارس أو كل شرط
في حلقات البرنامج. `swaps` عدد التبادلات. التبديل العادي يضيف كتابتين إلى `array_writes`.
`writes` إجمالي `array_writes + auxiliary_writes`.

### Selection Sort — `selection_sort`

- **الفكرة:** لكل خانة، تبحث عن أصغر قيمة في الجزء الذي لم يترتب بعد، ثم تبدلها إلى أول الجزء.
- **مثال:** `[4, 1, 3]`؛ تجد `1` وتضعه أولًا، ثم تختار `3` للموضع التالي.
- **المدخل:** قائمة أعداد صحيحة داخل `SortContext`.
- **النتيجة:** نفس القائمة بعد ترتيبها تصاعديًا؛ لا تنشئ قائمة ناتج منفصلة.
- **التعقيد:** أفضل/متوسط/أسوأ `O(n²)`، مساحة مساعدة `O(1)`.
- **الخصائص:** in-place، غير stable؛ يمكن تبديل قيم متساوية بطريقة تغير ترتيب سجلاتها لو كانت العناصر سجلات.

### Bubble Sort — `bubble_sort`

- **الفكرة:** تقارن كل زوج متجاور وتبدله لو كان معكوسًا. أكبر القيم تصعد تدريجيًا لنهاية الجزء.
- **التوقف:** يحتفظ بمكان آخر تبديل، فيتجاهل الجزء الذي صار مرتبًا. لو لم يحدث أي تبديل تنتهي.
- **التعقيد:** أفضل `O(n)`، متوسط/أسوأ `O(n²)`، مساحة `O(1)`.
- **الخصائص:** in-place وstable؛ لا يبدل المتساويين لأن الشرط يبدل فقط عند `>`.

### Odd-Even Sort — `odd_even_sort`

- **الفكرة:** تنفذ مرحلة لأزواج الفهارس `0-1, 2-3, ...` ثم مرحلة للأزواج `1-2, 3-4, ...`.
- **التوقف:** تكرر المرحلتين حتى تمر دورة كاملة دون تبديل.
- **التعقيد:** أفضل `O(n)`، متوسط/أسوأ `O(n²)`، مساحة `O(1)`.
- **الخصائص:** in-place وstable؛ التبديل بين المتجاورين يحافظ على ترتيب القيم المتساوية.

### Cocktail Sort — `cocktail_sort`

- **الفكرة:** نسخة ذهاب وإياب من Bubble Sort. تمر للأمام لتحرك الكبير لليمين، ثم للخلف لتحرك
  الصغير لليسار.
- **التوقف:** تضيق حدود الجزء في الاتجاهين. تنتهي إذا لم يحصل تبديل في أحد المسحين.
- **التعقيد:** أفضل `O(n)`، متوسط/أسوأ `O(n²)`، مساحة `O(1)`.
- **الخصائص:** in-place وstable.

### Insertion Sort — `insertion_sort`

- **الفكرة:** تعتبر الجزء الأيسر مرتبًا. تأخذ `key` من العنصر التالي، وتحرك العناصر الأكبر منه
  خانة لليمين، ثم تضع `key` في الفجوة.
- **ملاحظة العرض:** أثناء مقارنة `key`، قد تكون القيمة محفوظة خارج الخانات مؤقتًا؛ لذلك حدث
  المقارنة قد يشير لفهرس واحد فقط مع احتوائه على القيمتين.
- **التعقيد:** أفضل `O(n)`، متوسط/أسوأ `O(n²)`، مساحة `O(1)`.
- **الخصائص:** in-place وstable؛ لا يحرك القيم المساوية.

### Binary Insertion Sort — `binary_insertion_sort`

- **الفكرة:** مثل Insertion Sort، لكن تستخدم بحثًا ثنائيًا لتجد مكان إدخال `key` داخل الجزء
  المرتب، ثم تزيح العناصر الأكبر.
- **الفائدة والحد:** تقل المقارنات إلى `O(n log n)` على الإجمالي، لكن الإزاحات قد تظل
  `O(n²)`؛ لذلك متوسط وأسوأ زمنها في البيانات الحالية `O(n²)`.
- **التعقيد:** أفضل `O(n)` بسبب فحص سريع للعناصر المرتبة، متوسط/أسوأ `O(n²)`، مساحة `O(1)`.
- **الخصائص:** in-place وstable؛ البحث يضع القيمة الجديدة بعد القيم المساوية.

### Frequency Sort / Counting Sort — `frequency_sort`

- **الاسم هنا:** تعد القيم ثم تعيد بناء الأعداد تصاعديًا؛ **لا ترتب القيم حسب أكثرها تكرارًا**.
- **الفكرة:** تجد أصغر وأكبر قيمة، تنشئ عدادًا لكل قيمة في المدى، تحصي التكرارات، ثم تكتب القيم
  حسب العدد من الأصغر للأكبر.
- **مثال:** `[3, -1, 3, 0]` تصبح `[-1, 0, 3, 3]`.
- **التعقيد:** `O(n + k)` زمنًا و`O(k)` مساحة، حيث `k = max - min + 1`.
- **الخصائص:** ليس in-place وليس stable كسجلات؛ يدعم السالب، لكن المدى الفعلي `k` يجب ألا
  يتجاوز 100,000. الحد الأقصى للحجم 10,000.
- **القياسات:** يقارن لإيجاد أصغر وأكبر قيمة، ثم يسجل الكتابات في مصفوفة العد كـ
  `auxiliary_writes`.

### Shell Sort — `shell_sort`

- **الفكرة:** تعمل مثل insertion sort لكن تقارن عناصر تفصلها فجوة `gap`. تبدأ بـ`n // 2`، ثم
  تقسم الفجوة على 2 حتى تصل إلى 1.
- **الهدف:** نقل القيم لمسافات أبعد مبكرًا، ثم إنهاء الترتيب بفجوة 1.
- **التعقيد في هذه النسخة:** أفضل `O(n log n)`، متوسط غير محدد لهذا التسلسل، أسوأ `O(n²)`؛
  مساحة `O(1)`.
- **الخصائص:** in-place وغير stable.

### Heap Sort — `heap_sort`

- **الفكرة:** يبني max-heap، حيث القيمة الأكبر في الجذر. يبدل الجذر مع آخر عنصر في الجزء، يقلل
  حدود heap، ثم يعيد خاصية heap بعملية `sift_down`.
- **النتيجة:** بعد نقل الأكبر إلى النهاية مرات متتابعة، تصبح القائمة تصاعدية.
- **التعقيد المعلن لهذه النسخة:** أفضل `O(n)` عند البيانات المتساوية مع التوقف المبكر في
  `sift_down`؛ المتوسط/الأسوأ `O(n log n)`، مساحة `O(1)`.
- **الخصائص:** in-place وغير stable.

### Quick Sort — `quick_sort`

- **الفكرة:** تختار pivot بوسيط أول ووسط وآخر الجزء، ثم تقسّم العناصر إلى أصغر من pivot، مساوية
  له، وأكبر منه.
- **التنفيذ:** iterative (من دون استدعاء recursive)، ثلاثي الأقسام، وتضع الأجزاء الأكبر في
  قائمة انتظار داخلية كي تعالج الأصغر أولًا وتحافظ على مساحة المكدس.
- **التعقيد:** أفضل `O(n)` عندما تكون القيم متساوية، متوسط `O(n log n)`، أسوأ `O(n²)`؛ مساحة
  إضافية `O(log n)` لهذه النسخة.
- **الخصائص:** in-place وغير stable. اختيار median-of-three يساعد في اختيار pivot لكنه لا
  يضمن منع الحالة الأسوأ.
- **حد القبول:** رغم أن المتوسط النظري `O(n log n)`، تستخدم ميزانية الخدمة تكلفة `O(n²)` كحماية
  من الإدخال المعاكس؛ لذلك قد يرفض السيرفر حجمًا أقل من سقف 10,000.

## 6. التعقيد والقياس مش نفس الشيء

`O(n²)` أو `O(n log n)` وصف لنمو العمل مع كبر الإدخال، وليس وقتًا ثابتًا بالميكروثانية. الزمن
المقاس يتأثر بحجم وشكل القيم، تنفيذ Python، المعالج، حمل الجهاز، وعدد مرات القياس. لذلك:

- قارن الخوارزميات على **نفس المصفوفة** ونفس الجهاز.
- استخدم عدة قياسات، وراجع الوسيط ومدى `min` إلى `max`.
- لو نطاقات الأوقات متداخلة، اعتبر الفائز في الزمن غير مؤكد.
- الخوارزمية صاحبة أقل وسيط في حالة واحدة ليست بالضرورة الأسرع في حالة أخرى.
- بيانات `complexity` النظرية منفصلة عن حدود حجم التشغيل وميزانية قبول الطلب.

## 7. الحدود المهمة للفرونت

- القيم أعداد صحيحة من `-1,000,000,000` إلى `1,000,000,000`.
- الحجم العام حتى 10,000، لكن سبع خوارزميات سقفها 1,000؛ اتبع `max_size` من metadata.
- العرض بالأحداث يدعم حتى 128 عنصرًا، و20,000 حدث لكل خوارزمية.
- الـbenchmark يدعم 1–15 قياسًا و0–3 warmups.
- الـsuite يدعم حتى 12 تركيبة حجم ونمط.
- توجد ميزانية عمل إجمالية؛ استيفاء سقف الحجم وحده لا يضمن قبول الطلب.
- لا تحفظ بيانات المستخدم على الخادم في النسخة الحالية؛ الطلب يرجع مكتملًا ولا يوجد job ID.
